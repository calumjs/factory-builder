# Build

1. Take one approved, dependency-ready task. Read repository instructions, the permitted context, worker-handoff.md as a template, and the approved external task-specific handoff copy when supplied. Keep live notes in that copy, not the hashed template. For a laptop fallback, follow launch-guide.md's source, trust and exact-command preflight first.
2. Implement only within the task's allowed paths and actions. Implement owned tests and fixtures, and in-scope CI or test-map changes, at the project's real paths, preserving the project's existing CI and ignore policy; a factory template is not application coverage.
When a change alters seed data or fixtures, review it together with assertions in tests that also run against long-lived environments. Record each relevant test's data prerequisites, environment, owner and authorized setup/cleanup. A fresh CI database seeded by the change does not prove those rows exist in production. Preserve meaningful feature assertions: design data-independent long-lived checks or use an explicitly authorized isolated disposable fixture; if representative data or safe setup is unavailable, hand off the required check as BLOCKED rather than reseeding production or weakening it to pass.

For a changed multi-actor flow (for example notifications, handoff or approvals), inspect every actor the test signs in as even when seeds are unchanged. In the handoff, map the scenario to its acceptance check, actor roles, fixture-only dependencies, intended environment and whether that scenario is required there. Preserve the user's optional-check choices. Choose a project-fitted path before Verify: approved preprovisioned test actors on the actual target, or an authorized disposable representative environment with isolated actors and setup/cleanup. Confirm that actor roles and separation exercise the intended behaviour; replacing a second actor with the first can invalidate the check. Missing production actors do not authorize user creation, seeding, ad-hoc database writes or permission changes. Any proposed provisioning needs its own scoped authorization and supported project procedure.

A disposable or preview result covers only that environment and revision; it cannot satisfy a required production scenario. If no safe path exists for a required scenario, hand it off as BLOCKED with the missing actor or setup decision. Tags and filters may select tests, but must carry the exact excluded scenarios and their required/optional disposition into Release; they never grant a waiver by themselves.

3. Name the G2 change-targeted tests that cover the diff; add or update a test when none covers the changed behaviour. When execution is authorized, run the still-required G1/G2 locally before handing to Verify. Carry optional rows through as WAIVED with their recorded result.
4. Record the revision, changes, assumptions and checks actually run with status.py for the tested subject; keep durable logs outside this directory and reference them. List every touched hashed contract (including config or project test maps); if a reviewed contract must change, include only its selective manifest entry in that review. Run the authorized integrity check before the handoff.
5. Before any retry or fallback, inspect the run's terminal state, logs, expected artifact and branch/commit outcome. Retry only with a new hypothesis, within the same task budget, with no concurrent writers. Record worker/run provenance and remaining uncertainty in the approved external task-specific handoff copy.
6. ci/README.md and ci/job.example.py are adoption proposals: adapt them only within CI-integration scope, with a pinned builder helper outside the change checkout, keeping tested S separate from storage E.

## Exit
A reviewable change and a handoff with the exact revision and evidence.
